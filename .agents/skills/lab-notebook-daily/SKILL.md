name: lab-notebook-daily
description: Contribute concise daily lab notebook entries explaining scientific rationale and progress toward established goals, using available chat context, repository evidence, and supplied offline work. Supports the portable Lab Notebook CLI and backup-import workflow.
---

Create a faithful daily record in this repository's notebook. Read [the agent interface](../../../AGENTS.md) for commands and schema. Resolve the repository and notebook file from the current workspace, configuration, or the user; never assume a person's home directory, account name, or machine layout.

Collect the day's relevant conversation context, available explicitly authorized chat summaries, repository changes, tests, figures, and offline work supplied by the user. Use the user's local date; ask if a cross-midnight session makes the intended notebook date unclear. You cannot retrieve an entire ChatGPT history unless an available integration provides it. Say which sources were unavailable. Do not claim comprehensive coverage from a single chat.

Follow the **Entry writing standard** in AGENTS.md: write the entry body as short bullet points, normally 3–5. Allow roughly 100–200 words when substantive results warrant the space; use fewer when sufficient. Do not use narrative paragraphs. Select the day's most salient work across relevant projects so the owner can immediately recall it months later. Prioritize experiments, analyses, findings, decisions, substantive method changes, relevant meetings, and research planning. Emphasize each task's actual result, including key measurements or negative results and their scientific meaning. For software changes, identify the concrete analysis now possible without claiming an unmeasured physiological effect. Omit routine software checks and bookkeeping unless they affect scientific interpretation or explain a consequential blocker; put routine verification in `sources`. Do not pad entries with stock limitations, work not performed, or generic statements of importance. Use the concise, factual voice of Methods sections in Nature publications, with plain neuroscience and signal-processing language. First person is optional; use past tense for completed work and observations. Explain unfamiliar terms and omit AI jargon. Pair consequential steps with their scientific rationale and make concrete connections to established goals. Use short descriptive links to verified repository functions/files and figures, data, or protocols on the owner's configured artifact host, assuming reader access to those services. Include limitations when they affect interpretation and next steps when established, without repeating them across fields. Move supporting detail to attachments or `sources`. Use documented goals and reasoning; ask about material gaps or identify them briefly rather than inventing a justification. This applies equally to initial entries and revisions.

Follow **Figures and saved analysis sources** in AGENTS.md. Use only existing figures. Do not generate new figures, replot saved data, calculate new summaries, or run new analyses unless the user explicitly asks. Find existing reports through prior entries/chats, project documentation, and the configured private source catalog (optional default `private-data/source-catalog.json`) before asking for a path. Read and visually inspect the relevant PDF pages, then copy or extract existing figures unchanged, preserving axes, units, labels, colors, and uncertainty. If a figure is missing, omit it and record the gap in `sources`; never reconstruct it. Add brief scientific captions and source PDF/page/panel provenance; distinguish the analysis date from acquisition dates and reviews of earlier results. Use `turbo` for spectrograms only when their creation or modification is explicitly requested; preserve existing figures' colormaps when including them. Update the private catalog with inspected sources for later contributions. Keep draft figures private and embed them as portable attachments when saving an authorized entry. Never commit private source locations or figures or silently publish them.

Keep completed work, observations, interpretation, validation limits, and next steps distinguishable in the entry body. Record repository URLs/commit IDs, artifact identifiers, and test evidence in `sources`. A code change or synthetic test alone is not a verified scientific finding. Do not invent outcomes, infer physiological results from a figure title, or mark verification from an incomplete test. Prefer `unverified`, `observation`, or `in-progress` when evidence is limited. Mark `significant` only for actual milestones such as new repositories, architectural changes, or substantiated major findings.

Combine small related tasks; separate distinct projects when useful. Choose stable entry IDs such as `YYYYMMDD-project-session-key` so retries are idempotent. Existing IDs with different content require an intentional revision with `--replace`; inspect the existing entry first. Avoid embedding raw sensitive subject data, credentials, or local absolute paths. Reference protected data by deidentified dataset ID. Attach only relevant authorized files; originals are preserved.

When the user asks to contribute at the end of the day, that authorizes saving the entry to the configured private notebook. Validate with `contribute --dry-run`, then save with `contribute`. Inspect the saved entry via `read` and report its ID, projects covered, sources considered, and any gaps. No extra conversational approval is required for that authorized private save. Hook invocations alone do not authorize publication, Git pushes, messages, broad chat-history access, or changes to unrelated repositories.

When publication is explicitly requested, complete the post-publication draft cleanup in AGENTS.md immediately after verifying the reader edition and current private backup. Remove that publication's temporary daily drafts, brainstorms, previews, and duplicate attachments with recoverable deletion where available; preserve unpublished work, canonical history, original evidence, and source-catalog references. Showing a publication draft does not publish it or trigger its cleanup.

When updating the notebook website, follow **Preserve the notebook during live software updates** in AGENTS.md. Verify existing entries, original attachments, and revisions against a current private backup after reloading the live notebook. An empty browser store is not a replacement for an existing notebook. This software-update check does not authorize republishing research entries or overwriting newer work.

If the agent cannot access the canonical file or local service, produce the entry JSON using the same schema and explain how to import it through the CLI. Do not claim the website was updated. If only a browser-storage notebook exists, work from a user-provided backup, use `--notebook` to update that copy, and return the validated updated backup for explicit restore. Do not create a competing canonical notebook silently.
